# WeKnora 部署指南

本文档覆盖项目的两种部署形态：**Docker 部署**（容器化全栈运行）与**本地开发部署**（基础设施容器化 + 应用本地运行）。请根据用途选择：

| 形态                   | 适用场景                 | 应用运行位置             | 关键文件                                        |
| -------------------- | -------------------- | ------------------ | ------------------------------------------- |
| POC Docker 部署（推荐）    | 团队 POC / 内网演示 / 二开验证 | 容器（本仓库源码构建）        | `deploy/poc/`                               |
| 官方 Docker Compose 部署 | 拉取官方镜像快速搭建           | 容器（Docker Hub 镜像）  | `docker-compose.yml` + `.env`               |
| 本地开发部署               | 日常改代码、调试、跑测试         | 宿主机（Go + Vite 热重载） | `docker-compose.dev.yml` + `scripts/dev.sh` |

> Lite 模式（单二进制 + SQLite，零外部依赖）见 `docs/LITE.md`，不在本文范围。

---

## 一、前置条件

### Docker 部署（方式 A / B 共同要求）

- Docker Desktop（Windows/macOS）或 Docker Engine + Compose v2
- 磁盘空间建议 ≥ 20 GB（postgres/redis/docreader/应用镜像）
- Node.js ≥ 18 + npm（仅方式 A 需要，用于构建前端 dist）

### 本地开发部署

- Go ≥ 1.26（见 `go.mod`）
- Node.js ≥ 18 + npm
- Docker（运行 postgres / redis / docreader 等基础设施）
- 可选：`air`（后端热重载，`go install github.com/air-verse/air@latest`）
- 可选：Rust 工具链（构建 anydoc 进程内解析引擎时才需要）

### 模型服务

应用启动后需要在 Web 界面（或 DB）中配置模型。内网环境通过 Thor 网关接入，可用模型如 `jf-deepseek-v4`、`qwen3.7-max`（LLM）与 `text-embedding-v4`（Embedding）。**内网模型地址必须加入 `SSRF_WHITELIST`，否则模型请求会被 SSRF 防护拦截。**

## 二、Docker 部署

### 方式 A：POC 本地构建部署（deploy/poc，推荐）

独立于根 `docker-compose.yml` 的一套 POC 编排：app / frontend / docreader 全部由本仓库源码本地构建（镜像 tag 固定 `poc`），postgres / redis 使用固定 tag 基础镜像，数据卷带 `-poc` 后缀，与开发环境互不影响。配置全部集中在 `.env.poc`，compose 文件不漂移。

#### 1. 准备配置

```bash
cd deploy/poc
cp poc.env.example .env.poc
# 编辑 .env.poc，替换所有 <change-me> 占位符
```

关键配置项：

| 变量                              | 说明                                                               |
| ------------------------------- | ---------------------------------------------------------------- |
| `APP_PORT` / `FRONTEND_PORT`    | 默认 `18080` / `18081`，避开本地开发实例占用的 8080                            |
| `GOPROXY_ARG`                   | 构建用国内代理 `https://goproxy.cn,direct`                              |
| `DB_*` / `REDIS_PASSWORD`       | compose 内 postgres / redis 凭据                                    |
| `RETRIEVE_DRIVER`               | **必须为 `postgres`**（见「四、常见问题」第 1 条）                               |
| `JWT_SECRET` / `SYSTEM_AES_KEY` | 生产强度随机值，必填                                                       |
| `SSRF_WHITELIST`                | 至少包含内网 Thor 网关域名，如 `localhost,127.0.0.1,ai-thor-qa.innostic.com` |
| `LLM_*` / `EMBEDDING_*`         | 内置模型读取的 Thor 网关地址与密钥                                             |

#### 2. 构建并启动

```bash
# 在仓库根目录或 deploy/poc 下执行（Windows 用 Git Bash）
./poc.sh frontend-dist   # 宿主机构建前端 dist（build 的前置条件）
./poc.sh build           # 本地构建应用镜像（app/ui/docreader）
./poc.sh up              # 全量启动；migration 由 app 容器启动时自动执行
./poc.sh smoke           # 冒烟：检查 /health 与前端可达性
```

启动完成后：

- 后端 API：`http://localhost:18080`（健康检查 `/health`）
- 前端界面：`http://localhost:18081`
- MCP 端点：`http://localhost:18080/mcp/v1`（需 `X-API-Key` 头）

> **MCP 端点必须指向 app 端口（8080 / 18080），不能走前端 nginx 的 80 端口**。
> 前端 `nginx.conf` 只代理 `/api/`、`/files`、`/r/`、`/assets/`、`/embed/`，**没有 `/mcp`**，
> 请求落到 `location /` 的静态文件处理会返回 **405 Not Allowed**（响应头 `Server: nginx`）。
> 判断方法：看报错响应体——nginx 的 405 是 HTML，app 的鉴权失败是 JSON
> `{"error":"Unauthorized: ..."}`（后者说明端点已找对，只是 Key 不对）。

#### 3. 日常操作（poc.sh 命令集）

```bash
./poc.sh redeploy   # 改代码后一条命令重建 + 替换（build + up -d），日常最常用
./poc.sh logs       # 跟踪 app 日志
./poc.sh ps         # 服务状态
./poc.sh down       # 停止（数据保留在 named volume）
./poc.sh down --volumes  # 停止并清空数据卷（仅重置环境时使用）
```

幂等性说明：重复执行 `up` / `redeploy` 安全；postgres 数据在 named volume 中，重部署不丢。

#### 4. 数据库迁移

- **常规情况**：app 容器启动时 `AUTO_MIGRATE=true` 自动执行，无需干预。
- **注意**：golang-migrate 按版本号记录（schema_migrations 表），版本号已记录的历史迁移**不会重跑**。若需手工修正历史库（如补灌被跳过的迁移 SQL），需手动连接 postgres 执行，例如：

```bash
docker exec -i WeKnora-postgres-poc psql -U weknora -d weknora < migrations/postgres/000002_xxx.up.sql
```

### 方式 B：官方镜像 Compose 部署（docker-compose.yml）

使用 Docker Hub 官方镜像 `wechatopenai/weknora-app` / `weknora-ui` / `weknora-docreader` 全栈拉起，包含 searxng、minio、sandbox 等完整服务。

```bash
cp .env.example .env       # 按文件内 A~J 分组注释逐项填写
docker compose up -d       # 或使用启动脚本
make start-all             # 等价脚本方式（含环境检查）
```

常用命令：

```bash
make pull-images     # 拉取/更新镜像（WEKNORA_VERSION 控制 tag）
make docker-stop     # docker compose down
make check-env       # 环境配置检查
make migrate-up      # 手动执行数据库迁移
```

镜像版本由 `.env` 中 `WEKNORA_VERSION` 控制（`latest` 稳定版 / `main` 开发版 / 具体 git tag 如 `v0.7.0`）。

## 三、本地开发部署

形态：**postgres / redis / docreader 等基础设施跑在 Docker，Go 后端与 Vite 前端在宿主机本地运行**，改代码即时生效。

### 1. 准备配置

```bash
cp .env.example .env
# 按注释填写必填项（DB/Redis 密码、JWT_SECRET、SSRF_WHITELIST、模型密钥等）
```

### 2. 启动基础设施

```bash
make dev-start           # 启动 postgres + redis + docreader + langfuse（默认集）
```

可选 Profile（按需追加）：

```bash
make dev-start DEV_ARGS=--qdrant      # + Qdrant 向量库
make dev-start DEV_ARGS=--neo4j       # + Neo4j 图数据库（GraphRAG 需要）
make dev-start DEV_ARGS=--minio       # + MinIO 对象存储
make dev-start DEV_ARGS=--dex         # + Dex OIDC 认证
make dev-start DEV_ARGS=--full        # 全部可选服务
```

### 3. 启动后端（新终端）

```bash
make dev-app
```

脚本行为（见 `scripts/dev.sh` 的 `start_app`）：

- 自动把容器服务地址映射到 `127.0.0.1`（DB_HOST、REDIS_ADDR、DOCREADER_ADDR 等）；
- 本地存储路径自动改用仓库内可写目录 `.local-data/files`（容器内的 `/data/files` 在宿主机不可写）；
- 检测到 `air` 时进入热重载模式，否则以 `go run` 启动（默认占用 8080 端口）；
- 检测到 anydoc 静态库时自动加 `-tags anydoc`。

后端启动后可访问 `http://localhost:8080/health` 与 Swagger（`/swagger/index.html`）。

### 4. 启动前端（新终端）

```bash
make dev-frontend        # Vite 开发服务器，http://localhost:5173，支持热重载
```

### 5. 状态与停止

```bash
make dev-status          # 服务状态
make dev-logs            # 基础设施日志
make dev-restart         # 重启基础设施
make dev-stop            # 停止所有基础设施容器
```

也可以使用一键脚本 `./scripts/quick-dev.sh`（单终端启动全套）。

### 6. 断点调试

`make dev-app`（`go run` / air）不适合调试：`go run` 会 fork 临时子进程、air 热重载不断换 PID，无法稳定 attach。调试请用 IDE 直接启动 `cmd/server`（项目已内置 `.vscode/launch.json`）：

**VS Code**：先 `make dev-start` 拉起基础设施，然后 F5 选择「Debug WeKnora (本地开发)」。launch 配置已复刻 dev.sh 的环境处理（读取 `.env`，并把 DB_HOST/REDIS_ADDR 等容器服务名覆盖为 `127.0.0.1`），行为与 `make dev-app` 一致。已通过 `make anydoc-lib` 构建过 anydoc 静态库时，选「Debug WeKnora (anydoc 引擎)」。

**GoLand**：新建 Go Build 运行配置，指向 `cmd/server`，Working directory 设为仓库根，Environment 中同样填入 launch.json 里的覆盖变量（或先用 `set -a && source .env && set +a` 思路在 GoLand 的 EnvFile 插件里挂 `.env`）。

注意：调试前必须保证基础设施容器在运行（launch 配置不会启动它们）；Windows 本机若 `go build` 因 pg_query cgo 失败，需先配好 MinGW-w64 工具链再调试。

### 7. 远程基础设施模式

基础设施部署在远程机器时，设置 `DEV_REMOTE_HOST=<远程IP>`（或写入 `.env.local`），`dev-app` 会将各服务地址指向该主机，并预先检测 5432/6379/50051 端口连通性。

### 7. 与 POC 环境共存

本地开发实例默认占用 `8080`（后端）/ `5173`（前端），POC 环境占用 `18080` / `18081`，数据卷与容器名均带 `-dev` / `-poc` 后缀，两套环境可同时运行、互不影响。

## 四、常见问题与排障

1. **search_chunks 0 命中 / embeddings 表不存在**  
   `RETRIEVE_DRIVER` 为空或未设为 `postgres` 时，系统跳过向量库初始化，embeddings 表缺失。POC 环境 `.env.poc` 必须显式设置 `RETRIEVE_DRIVER=postgres`，修复后需对已有文档重新解析（reparse）。
2. **模型请求被拦截（SSRF）**  
   内网模型网关（如 `ai-thor-qa.innostic.com`）未加入 `SSRF_WHITELIST`。app 与 docreader 共用该变量，修改后需重启对应容器。
3. **`./poc.sh build` 报 frontend/dist 不存在**  
   POC 前端镜像构建依赖宿主机预构建产物，先执行 `./poc.sh frontend-dist`。
4. **文档解析卡在 finalizing**  
   上传后 Docker Desktop 被关闭/暂停会打断解析管线（asynq 任务）。重新启动 Docker 后任务会自动恢复续跑，无需重传。
5. **Windows 本机构建失败：`build constraints exclude all Go files`（sqlite-vec / duckdb / pg_query 等）**  
   根因是**本机没有 C 编译器**：这些包依赖 cgo，gcc 缺失时 Go 自动置 `CGO_ENABLED=0`，cgo 源文件被构建约束排除，报错形态即 "build constraints exclude all Go files"（VS Code F5 调试与 `make dev-app` 原生运行同样命中）。解决：`choco install mingw -y` 安装 MinGW-w64（需管理员权限），重开终端确认 `gcc --version` 可用后重新构建。首次编译 duckdb 绑定耗时较长属正常。完整构建也可放 Docker（Linux）内进行；本地仅做语法检查可用 `gofmt -l -e`。
6. **迁移不生效**  
   golang-migrate 按版本号记录，历史版本不会重跑（见二.A.4）；确认 `schema_migrations` 表中 dirty 标记与版本号。
7. **端口冲突**  
   `8080`：本地 dev 后端或官方 compose 的 app；`18080`/`18081`：POC。冲突时优先调整 `.env.poc` 的 `APP_PORT` / `FRONTEND_PORT`。
8. **Windows 提示 `make: command not found`**  
   Windows 的 Git Bash 不自带 make。两种解决方式任选：
   - **不装 make，直接用脚本**（Makefile 的 dev 命令只是 dev.sh 的薄封装）：
     ```bash
     ./scripts/dev.sh start        # 等价 make dev-start，可带 --neo4j 等 Profile
     ./scripts/dev.sh app          # 等价 make dev-app
     ./scripts/dev.sh frontend     # 等价 make dev-frontend
     ```
     注意 dev.sh 是 bash 脚本，须在 **Git Bash** 中运行（PowerShell/cmd 不行）。
   - **安装 make**：`choco install make -y`（需管理员权限）。注意 **make 也必须在 Git Bash 中运行**：Windows 原生 make 在 PowerShell/cmd 下会用 cmd.exe 作 shell，`uname` / `bash` 全部找不到，报 `CreateProcess(...) failed`（Makefile 平台探测与 dev-start 目标均失败）。装完后在 **Git Bash** 中重开终端执行 `make dev-start`。
9. **目标主机 CPU 不支持 AVX2：postgres 反复重启 / 日志 SIGILL（exit 132）**  
   ParadeDB 的 `pg_search.so` 由 Rust(pgrx) 构建并含 AVX2 指令，在仅支持 SSE2 的老式 CPU（典型如 QEMU v2.5 虚拟 CPU）上一加载即 `SIGILL`。判定与处理：
   - **症状**：postgres 容器不断重启；日志出现 `Illegal instruction`；`dmesg` 可见 `traps: postgres[..] trap invalid opcode`。注意 `initdb` 阶段就会触发——ParadeDB 镜像的 `postgresql.conf.sample` 预置了 `shared_preload_libraries='pg_search,...'`，`initdb` 的 bootstrap 后端会加载它。
   - **确诊**：`grep -o 'avx2\|sse4_2\|popcnt' /proc/cpuinfo | sort -u`（本机仅 `sse2` 即命中）；`strace` 可见打开 `pg_search.so` 后立刻 SIGILL。
   - **处置**：该 CPU 上 bm25 **无法启用**（`CREATE EXTENSION pg_search` / `LOAD 'pg_search'` 同样 SIGILL），需整体跳过并保留语义检索，步骤：
     1. postgres 用 `postgres-paradedb:v0.22.2-pg17-x86base` 镜像（见 `deploy/poc/docker/Dockerfile.paradedb-x86baseline`）：以 pgdg 官方 bin 替换自编译后端，并从 `postgresql.conf.sample` 删除 `shared_preload_libraries` 中的 `pg_search` 预加载，使 `initdb` 能通过。
     2. 数据恢复时过滤掉 `pg_search` 与 bm25 相关索引（`embeddings_search_idx`）的 TOC 条目，否则 `pg_restore` 会失败。
     3. `.env.poc` 设 `KEYWORD_RETRIEVAL_DEGRADED=1`：关键词腿失败时返回空结果，混合检索降级为**纯向量检索**，而不是整个请求报错。正常环境保持不设置以维持 fail-fast。
   - **保留能力**：`vector`(pgvector/HNSW) 等纯 C 扩展不受影响，语义检索完全可用。首次启动后确认 `select extname from pg_extension;` 中有 `vector` 且检索接口返回 200。
10. **MCP 客户端连不上（405 Not Allowed / Unauthorized）**  
    端点必须指向 **app 端口**，不能走前端 nginx。迁移换主机时最容易把端口漏掉：本机是 `http://localhost:18080/mcp/v1`，目标机是 `http://192.168.0.38:8080/mcp/v1`，**若写成 `http://192.168.0.38/mcp/v1`（不带端口）会默认走 80**。目标机前端已改为 `18081` 后，80 上没有任何监听，这种写法现在直接**连接被拒**（此前前端占 80 时表现为 nginx 的 405）。
    - 快速区分三类失败：

      | 现象 | 响应特征 | 含义 |
      | --- | --- | --- |
      | `405 Not Allowed` | HTML，`Server: nginx` | 打到了前端 nginx（端口写成了 `18081`），**端点/端口错** |
      | 连接被拒 / `000` | 无响应 | 端口上没有服务（如裸写 80），**端口错** |
      | `401 Unauthorized` | JSON `{"error":"Unauthorized: missing authentication"}` | 端点正确，**缺 `X-API-Key` 头** |
      | `200` + `serverInfo` | JSON `{"name":"weknora","version":"poc"}` | 正常 |

    - 自查命令（期望 200 并返回 `serverInfo`）：
      ```bash
      curl -i -X POST "http://192.168.0.38:8080/mcp/v1" \
        -H "X-API-Key: <key>" -H "Content-Type: application/json" \
        -H "Accept: application/json, text/event-stream" \
        -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"t","version":"1"}}}'
      ```
    - 客户端配置在 `~/.workbuddy/mcp.json`（`weknora-poc-read` / `weknora-poc-write`）。**改完 URL 或 Key 后 MCP 不会自动重载，需在连接器管理页重新「信任」该服务**。
    - 若确实希望只用 80 端口暴露 MCP，需在 `frontend/nginx.conf` 增加代理段后重建前端镜像（注意 MCP 走 SSE，应参照 `/api/` 段关闭 `proxy_buffering`）：
      ```nginx
      location /mcp/ {
          proxy_pass ${APP_SCHEME}://${APP_HOST}:${APP_PORT}/mcp/;
          proxy_set_header Host $host;
          proxy_http_version 1.1;
          proxy_set_header Connection "";
          proxy_buffering off;
          proxy_read_timeout 3600s;
          proxy_send_timeout 3600s;
      }
      ```

## 五、POC 目标主机部署记录

POC 验证完成后迁移至独立主机，作为对外演示环境。

### 5.1 环境信息

| 项 | 值 |
| --- | --- |
| 主机 | `192.168.0.38`（Ubuntu，账号 `ubuntu`，SSH 22） |
| 镜像仓库 | `inno-tcr.tencentcloudcr.com/innostic/poc/` |
| 访问入口 | 前端 `http://192.168.0.38:18081/`（**必须带 `:18081`**，见下方说明）、后端 API `http://192.168.0.38:8080/` |
| MCP 端点 | `http://192.168.0.38:8080/mcp/v1`（**必须带 `:8080`**，见下方说明） |
| PostgreSQL | `192.168.0.38:5432`（`POSTGRES_EXPOSE_PORT=5432`，按需对外） |
| 部署目录 | `~/weknora-poc/`（含 `docker-compose.poc.yml`、`.env.poc`、`migrate/`） |
| CPU 约束 | 仅 SSE2（**无 AVX2**）→ bm25 不可用，见 FAQ 9 |

> **前端端口不用 80**：该主机上 80 端口不作 WeKnora 前端入口（`.env.poc` 里 `FRONTEND_PORT=18081`，与 `deploy/poc/poc.env.example` 的默认值一致，也和本机 POC 实例的 `18080`/`18081` 命名保持统一）。容器内 nginx 仍监听 80，仅宿主映射端口不同：`0.0.0.0:18081->80/tcp`。若此前在目标机上把 `FRONTEND_PORT` 改回过 `80`，属于与模板的漂移，改回 `18081` 后按 5.6 的方式只重建 frontend 即可。

镜像与容器映射（compose 中所有 `image:` 均指向 TCR，目标机只 `pull` 不构建）：

| 服务 | 镜像 | 容器名 |
| --- | --- | --- |
| app | `poc/weknora-app:poc` | `WeKnora-app-poc` |

### 5.3 数据迁移

- **数据库**：`pg_dump -Fc` 导出后 `pg_restore`。目标机 pg_search 不可用，需先过滤 TOC：
  ```bash
  pg_restore -l dump > toc.list
  grep -viE "pg_search|embeddings_search_idx" toc.list | grep -v "^;" > toc.filtered
  pg_restore -U weknora -d weknora -L toc.filtered dump
  ```
- **文件卷**：`data-files` 卷打包 tar 后，在目标机以 `--user 0` 解压（卷内文件属主为 root）：
  ```bash
  docker run --rm --user 0 -v weknora-poc_data-files-poc:/dst -v $PWD:/src alpine \
    sh -c "tar xzf /src/data-files.tar.gz -C /dst"
  ```

### 5.6 增量发布（只改了前端时）

改前端（图标、文案、页面等）**不要重建 app 镜像**——`Dockerfile.app` 全量重建约 1h15m，而前端镜像只有 nginx + 静态文件，**全程约 2 分钟**。

```bash
cd <repo>
# 1) 宿主机产出 dist（前端镜像靠 COPY dist，必须先构建）
bash scripts/build_frontend_dist.sh        # 依赖 node/npm；等价 ./poc.sh frontend-dist

# 2) 构建并双 tag 前端镜像
docker build -t weknora-ui:poc \
  -t inno-tcr.tencentcloudcr.com/innostic/poc/weknora-ui:poc frontend/
docker push inno-tcr.tencentcloudcr.com/innostic/poc/weknora-ui:poc

# 3) 目标机替换（只动 frontend，其余容器不受影响）
ssh ubuntu@192.168.0.38
cd ~/weknora-poc
docker compose --env-file .env.poc -f docker-compose.poc.yml pull frontend
docker compose --env-file .env.poc -f docker-compose.poc.yml up -d frontend
```

验证发布是否生效（`size` 与 `md5` 应等于新文件）：

```bash
curl -s -I http://192.168.0.38:18081/favicon.ico | tr -d '\r' | grep -iE "content-length|content-type"
curl -s http://192.168.0.38:18081/favicon.ico | md5sum
```

两个注意点：

- **`npm run build` 前若 `frontend/dist` 已存在大批旧文件**，个别受限环境会阻止 vite 清空该目录（批量删除保护）。此时手动让 dist 消失再构建即可（dist 被 gitignore，是纯产物，删除可随时重建）：`mv dist dist.bak && npm run build`。
- favicon 在 `location /` 命中，带 `Cache-Control: no-cache, must-revalidate`，服务端会立即更新；但**浏览器对 favicon 缓存较顽固**，请用 `Ctrl+F5` 强制刷新或换隐私窗口确认。

#### ⚠️ `--env-file .env.poc` 一个字都不能省

目标机上配置文件叫 **`.env.poc`**，不是 compose 默认自动加载的 `.env`。一旦漏掉 `--env-file .env.poc`：

1. compose 会把所有 `${DB_USER}` / `${DB_PASSWORD}` / `${DB_NAME}` 解析成空串（日志里刷 `variable is not set. Defaulting to a blank string`）；
2. `frontend` 通过 `depends_on` 关联 app，compose 认定依赖服务的配置已变化，于是**把 redis / postgres / docreader / app / frontend 全部重建**，而不是只动 frontend；
3. 重建后的 app 因为拿不到数据库账号密码而启动失败（`dependency failed to start: container WeKnora-app-poc is unhealthy`），整个站点 502。

**急救**（数据在命名卷里，重建容器不会丢数据，补上 env 文件重启即可）：

```bash
cd ~/weknora-poc
docker compose --env-file .env.poc -f docker-compose.poc.yml up -d
# 之后核对：5 个容器 Up/healthy + 数据计数没归零
```

**判据**：`up -d` 的输出里出现 `Container WeKnora-xxx Recreate` 且 xxx 不只是 frontend，就说明 env 文件漏了，应立刻中断并补上。

#### 构建前端时 `mv dist` 报 `Device or resource busy`

说明有进程把 `frontend/dist` 当成了工作目录，多半是上一轮验证时起的静态预览服务（`python -m http.server`）残留。定位并结束它即可：

```bash
netstat -ano | grep LISTENING | grep <端口>   # 拿到 PID
tasklist /FI "PID eq <PID>"
taskkill /PID <PID> /F
```

### 5.7 登录页线上验证（Chrome DevTools Protocol）

`deploy/poc/migrate/verify_login_page.mjs` 用无头 Chrome 对**已发布**的登录页做程序化校验，覆盖肉眼/截图看不出来的问题：

```bash
node deploy/poc/migrate/verify_login_page.mjs http://192.168.0.38:18081/ .tmp/verify
# 产物：.tmp/verify/verify-report.json + 三种视口截图（含一张深色主题）
```

它检查三件事：

1. **页脚备案号链接**的 `href` / `target` / `rel` / 文案，以及桌面、平板、手机三档视口下的实际间距；
2. **是否真的点得着**——对链接中心点做 `elementFromPoint` 命中测试。页脚容器是 `pointer-events: none`（避免窄视口挡住下方元素），只放开链接本身；如果忘了放开，截图上看不出任何异常，但点击完全无反应，**只有命中测试能发现**；
3. **悬停态**——用 `Input.dispatchMouseEvent` 真发鼠标移动事件，再读 `:hover` 的计算样式；以及深色主题下 logo 的 `filter` 是否仍为 `none`（历史遗留的反色滤镜会毁掉品牌配色）。

两个坑已内置处理：页脚绝对定位在文档最底部，**在首屏之外**，必须 `scrollTo` 到底再做命中测试，否则视口外坐标一律返回 `null`，会把"没点着"误判成样式问题；新用户引导弹窗的全屏遮罩会干扰命中测试，故通过 `Page.addScriptToEvaluateOnNewDocument` 预置 `localStorage` 标记关掉它。

注：之所以不用"iframe 探针页 + 截图"，是因为探针页与目标页跨源、读不到 iframe 内的 DOM；CDP 的 `Runtime.evaluate` 直接跑在目标页上下文，没有同源限制。
