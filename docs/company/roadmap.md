# 企业化预研路线图

## 1. 阶段总览

```text
P0 真实源码和 Git 基线
  -> P1 单主 Tenant、企业微信只读同步
  -> P2 身份映射 dry-run
  -> P3 身份映射持久化和受控成员投影
  -> P4 部门权限计算 POC
  -> P5 确认授权算法后再实现 ACL
  -> 后续：登录、生产化和官方版本同步
```

当前已接入源码和 Git 基线，并完成关键认证/授权源码的静态核对及设计修订；构建、基础测试、POC 和真实接口回归尚未完成，P0 不算全部完成。本次只修订设计，不进入功能或 ACL 实现。

本次设计修订顺序为：资源范围门槛和部门 grant 局部上限 -> 身份来源及事实时效 -> 同步计划/回滚版本 -> 固定矩阵和真实入口。此设计顺序不改变下述功能阶段准入。

## 2. P0：真实源码和 Git 基线

产物：

- 完整的 `BlankPeng/Weknora-Bp` 源码；
- 基于完整源码创建的 `develop-company`；
- 企业化架构设计和本预研文档；
- 可复现的源码提交、版本和迁移基线。

完成条件：

1. `develop-company` 与完整源码存在共同祖先；
2. `git merge-base` 有结果；
3. 项目可以构建；
4. 基础测试可以运行；
5. 公司一期采用单主 Tenant；
6. Tenant RBAC、资源归属、组织共享和 API Key 的权限上限已确定；
7. 外部身份状态传播规则已确定；
8. 二开远程、公开材料边界和官方同步策略已确定；需要保密的公司材料使用独立私有仓库，不推送到当前公开 Fork。

当前基线记录：

```text
main        -> d9585f75b25cb20c62cceada7fa0069d3a50c97d
origin/main -> d9585f75b25cb20c62cceada7fa0069d3a50c97d
vendor/main -> d9585f75b25cb20c62cceada7fa0069d3a50c97d
develop-company -> 从 origin/main 建立的二开集成分支
docs/company-org-permission -> 从 develop-company 建立的设计分支
codex/archive/company-design-draft -> 本地旧设计历史与最新原稿归档
```

二开集成分支和设计分支均继承上述源码基线；远程 `main` 保持不变。原来没有共同祖先的旧设计历史只在本地归档，不合并到源码历史。共同祖先已建立不代表 P0 全部完成，在构建、测试和关键设计边界确认前，仍不得进入功能开发。

## 3. P1：单主 Tenant、企业微信只读同步

范围：

- 企业微信部门树拉取；
- 用户和部门关系拉取；
- 分页、限流、重试；
- 规范化输出；
- 脱敏差异报告。
- 只面向公司一期主 Tenant 生成投影计划。

禁止：

- 写 `users`；
- 写 `tenant_members`；
- 写任何 `identity_*` 表；
- 自动创建组织；
- 自动创建多个 Tenant；
- 自动赋予权限；
- 自动停用用户。

退出条件：

- 固定样本和真实脱敏样本都能重复生成相同结果；
- 分页末页和异常中断行为有测试；
- 组织树无循环；
- 用户外部 ID 唯一；
- 失败时没有撤销动作。
- 采集代次在请求开始前分配，完整可见列表与权威删除证据分开；
- 外部可见范围缩小时不把失联自动判为 deleted。

## 4. P2：身份映射 dry-run

范围：

- 建立外部身份到本地用户的候选映射；
- 只使用内存模型和固定脱敏样本；
- 输出新增、更新、冲突和无法匹配清单；
- 验证邮箱、用户名和人工确认规则；
- 验证用户跨部门关系。
- 验证邮箱双侧归属证据和多身份源的来源选择；
- 在内存中固定来源/目标版本、计划 hash、审批有效期并输出旧计划冲突。

退出条件：

- 不会重复创建本地用户；
- 冲突必须人工处理；
- 映射可以撤销；
- 所有差异都有批次号。

## 5. P3：身份映射持久化和受控成员投影

### 5.1 P3-A：持久化最小身份映射

范围：

- 在确认匹配、冲突和撤销后，评审映射及最小来源版本/计划/贡献元数据；不要求持久化完整外部快照；
- 稳定记录 `provider_id`、`external_user_id`、`local_user_id`、`match_method`、状态、最近验证批次和 rebind 历史；
- 保证一个身份源中的外部身份最多只有一个 active 映射；
- 保证一个身份源中的一个本地用户最多只有一个 active 外部账号；不同身份源可以绑定同一本地用户；
- 冲突、未确认和 revoked 映射不能进入成员投影；
- 记录 provider 进入 degraded 的时间，支持区分降级前签发和降级后签发的 Token；
- 会话可信记录认证来源，刷新与切换 Tenant 不自动换来源；优先复用现有 Token 撤销，不预定新增 `session_epoch`；
- 不要求同时持久化完整部门快照或 `permission_bindings`。

固定冲突样本：

```text
同一 provider：
    external_user E1 -> local_user U1
    external_user E2 -> local_user U1
```

预期结果：第一条映射可以按批准规则进入 active；第二条映射进入 `conflict`，不能自动 active，必须人工重新匹配或确认。不同 provider 绑定同一 `local_user` 仍然允许，但每个 provider 内最多一个 active 外部账号。

退出条件：

- 同一外部身份重复同步不会产生第二个 active 映射；
- 邮箱、姓名等候选匹配不能绕过冲突人工确认；
- disabled 保留绑定但撤销该来源贡献；deleted 须完整范围核对及权威证据才可 revoked；
- 本地账号封禁、单来源失效和全部旧会话撤销已区分，验证 P1 停用/P2 新登录只使用 P2 和人工贡献；
- 现有 Token 撤销或获准扩展覆盖用户全部旧 access/refresh Token，并发签发/刷新与撤销共享屏障；
- API Key 独立撤销，候选用户绑定 Key 的全部旧凭证不随新来源登录复活；
- revoked 映射重新出现时创建新绑定记录，保留旧记录和审计关系；
- `external_department` 权限主体使用 `provider_id + subject_ref` 命名空间；
- 映射变更可以关联到同步批次并可回滚。
- 旧 active 计划在新 disabled 已应用后返回 stale_plan、零写入；审批/配置/范围/目标变动须新计划；
- rollback 校验版本、归属及 ABA，不恢复安全停用、已撤销会话/Key；所有实际写入路径维护版本。

### 5.2 P3-B：受控成员投影

范围：

- 在 feature flag 下创建或更新现有 `tenant_members`；
- P3-B 只能消费 P3-A 已确认的 active 映射，且外部用户当前状态必须为 `active`；
- 默认只授予 `viewer` 或 `contributor`；
- 停用/删除只撤销该来源拥有的成员/部门贡献，重算投影，不覆盖其他有效来源和人工贡献；
- 写审计日志；
- 提供 dry-run、apply、rollback；
- apply 全量预检后逐对象 CAS；中途冲突标记 partial，不静默重算/重放；
- rollback 只撤销仍归本 change 拥有的变更，人工变更或值改回原目标的 ABA 均冲突。

绝不自动做：

- 授予系统管理员；
- 授予 Owner；
- 创建 API Key；
- 修改知识库归属；
- 删除用户历史数据；
- 覆盖人工角色、人工授权或 `break-glass` 权限。

## 6. 后续候选：登录和会话联动

登录方案候选：

1. 企业微信 OAuth/OIDC；
2. 统一身份平台 OIDC；
3. 企业微信只做组织同步，登录仍使用现有账号体系。

决策顺序：

```text
先确认身份匹配和撤销机制
    -> 再确定登录协议
    -> 最后接入登录路由
```

验收重点：

- 首次登录不会创建重复账号；
- 用户停用后已有会话失效；
- 账号绑定可审计；
- 登录失败不会泄露外部身份信息。

该阶段不属于当前主路径，必须在身份映射、状态传播和撤销规则稳定后再单独评估。

## 7. P4：部门权限计算 POC

先用策略计算器和固定数据验证，不立即改路由。

必须验证：

- 多部门权限可以取并集；
- 单主 Tenant 资源范围门槛按“用户、资源、action、路径”判断，未绑定默认拒绝；
- tenant_public 仅开放声明动作给源 Tenant 成员，人工 admin 范围例外不豁免硬阻断；
- 部门动作限制只裁剪部门 grant，人工 admin 同时属于普通部门时管理能力不丢失；
- 并集不能突破 Tenant RBAC；
- 并集不能突破资源归属；
- 组织共享不能绕过源空间安全边界；
- API Key 不能获得未声明能力；
- 停用、撤销和过期始终硬阻断；
- Tenant 成员、组织共享、共享 Agent 和 API Key 分路径计算，不跨主体合并；共享和 Agent 不能绕过内部部门门槛；
- 父部门默认不向子部门继承，显式继承后才重新计算；
- 部门移动后旧授权撤销、新授权按新部门重新计算；
- 部门负责人只能查看、查询和编辑明确绑定的知识库内容，且不能自动突破资源归属；
- 部门负责人不能删除知识库、共享知识库、管理空间成员或修改空间设置；
- 临时授权；
- 授权过期；
- 外部同步失败保护；
- `provider_degraded` 与外部用户 `disabled/deleted` 状态分离；
- healthy/degraded 均检查 `now-last_verified_at`，降级再检查周期年龄和旧 Token 签发时间；最后确认 25h、降级 2h 必须拒绝；
- 本地会话撤销状态不可读时 fail-closed；
- API Key 独立撤销不依赖真人会话版本。
- P1 停用/P2 有效时全部旧会话及绑定 Key 拒绝，P2 新会话不继承 P1 部门 grant；
- 旧计划不能恢复新停用，回滚不能越过版本/所有权和安全状态。

固定夹具统一使用 permission-design.md 第 13 节：主 T0、接收 T1、P1/P2、U1-U9、K1-K6、O1、A1、AK1/AK2。固定用户 Tenant 角色、组织 Tenant 角色、共享/导出权限、认证来源及确认/降级/签发/到期时间；T1 只用于共享验收，不按部门创建额外公司 Tenant。

POC 输出主体、认证来源、访问路径、资源、action、结果、范围命中/拒绝、grant、ceiling、状态/策略版本和时间依据，不能只输出角色数字。授权算法只采用 permission-design.md 第 6 节，不在计算器自行增补隐含许可。

通过门槛：

1. 未授权放行为 `0`；
2. 已确认应允许场景的误拒绝为 `0`；
3. 停用、删除、撤销和过期后的继续放行为 `0`；
4. 连续两次 dry-run 的结果、命中来源和计数一致；
5. 所有矩阵项均为 `allow`、`deny` 或 `deny_with_gap`，不能有 `unknown`；
6. 部门负责人非创建者编辑场景如果只能被资源归属守卫拒绝，必须明确记录能力缺口，不能以修改核心 RBAC 方式通过；
7. `provider_degraded` 的进入阈值、恢复阈值、`max_stale_age` 和本地 fail-closed 条件均有结果；
8. 降级前签发 Token 与降级后签发/刷新的 Token 得到不同且可重复的结果；
9. P3-A 的两条 active 唯一约束和 `provider_id` 主体命名空间均有验证；
10. `degraded_at` 在进入、重复失败和恢复三个状态转换中的时间语义符合设计。
11. 未绑定、公有动作、人工 admin、共享 Agent 和多身份源回归全部有明确结果；
12. 25h/2h 反例、24h 边界、缺失/未来时间、来源缺失及已撤销用户绑定 Key 不产生允许；
13. 案例预期是可复现输入的一部分，不将本次静态公式演算当作 P4 已完成。

P4 不用一个“通过/不通过”掩盖能力缺口，采用三种结果：

| P4 结果 | 判定 | 后续 |
| --- | --- | --- |
| `fail` | 有未授权放行、应允许误拒绝、撤销后继续放行或 `unknown` | 不进入 P5 |
| `security_pass_with_gap` | 硬阻断、ceiling 和路径组合正确，但存在明确 `deny_with_gap` | 只能为无缺口 capability 进入 P5；缺口能力不能发布 |
| `pass` | 本次声明范围内没有未决 `deny_with_gap`，所有结果已确认 | 可进入完整 P5 评审 |

`deny_with_gap` 必须有缺口说明、影响范围、责任人、复核日期和临时限制，并由业务负责人和权限/安全评审人共同批准。未经批准的缺口按 `fail` 处理。

## 8. P5：确认授权算法后再实现 ACL

只有 P4 达到 `pass` 或 `security_pass_with_gap` 后，才允许在对应范围内实现部门 ACL 或评估 `permission_bindings`：

1. 先固化硬阻断规则；
2. 再固化资源/action/路径范围门槛和未绑定、公共、管理员、跨 Tenant 导出规则；
3. 固化来源 grant 的局部限制、路径共同上限和合法路径合并规则；
4. 明确部门策略禁止授予的能力；
5. 用现有 Tenant RBAC、资源归属、组织共享和 API Key 测试回归；
6. `security_pass_with_gap` 只能实现无缺口 capability，不得实现或发布缺口对应能力；
7. 最后才决定代码位置和数据库迁移。

P5 接入与发布门槛：

- 建立路由/服务入口清单，覆盖 KB/Agent 列表、计数、分页、详情、检索、聊天、Agent 工具、子资源、下载、图片/引用代理、缓存与后台任务；
- 同 Tenant KB 直接放行、组织共享、共享 Agent 的 all/selected/none、显式/省略 agent_id 都经同一资源范围决策器；
- 显式请求任一越界 KB 的批量检索整次拒绝；动态 all 范围只展开可授权集合，检索和引用均不泄露内容；
- 强制 Tenant RBAC 与公司范围检查，观察模式不能作为隔离生产配置；系统管理员/API Key 例外单独验收；
- 实际 HTTP/集成测试同时证明未授权放行 0、应允许误拒绝 0、撤销后继续放行 0，缓存和流式任务也重新验证；
- P4 计算器与本轮文档检查不代替上述集成证据，未接入入口或未验收能力不得宣称已交付。

在 P5 之前，不修改现有 RBAC 中间件，不增加部门 ACL 路由，不增加权限迁移；`security_pass_with_gap` 也不能解锁生产发布。

## 10. 风险和应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 外部 ID 匹配错误 | 用户串号、权限泄露 | 显式映射、冲突人工确认 |
| 外部 API 分页不完整 | 错误停用大量用户 | 短页/空页校验、全量对账 |
| 误把部门当租户 | 资源和空间爆炸 | 部门先做策略主体 |
| 角色直接映射 Owner | 越权 | Owner 只允许人工或受控流程 |
| 同步失败触发删除 | 大范围拒绝服务 | 失败保护和停用延迟 |
| 修改核心 RBAC | 官方合并困难 | 适配层和最小扩展 |
| 把 Secret 写入配置表 | 凭据泄露 | 只保存密钥引用 |
| grant 并集被当作资源隔离 | 同 Tenant 越权可见 | 独立范围门槛及全入口检查 |
| 部门动作限制裁剪人工 admin | 管理误拒绝 | 仅裁剪部门 grant、保留共同安全上限 |
| 保留 active 绕过事实时效 | 过时身份继续访问 | healthy/degraded 分支显式检查事实年龄 |
| 旧审批/回滚恢复新停用 | 权限复活 | 来源/目标版本、CAS、变更归属及安全栅栏 |

## 11. 当前明确不做的事项

- 不新增 `organization_department`、`organization_user` 这类重复核心表；
- 不把企业微信部门硬编码到 Go 枚举；
- 不把企业微信管理员直接映射为 WeKnora Owner；
- 不替换现有 `RequireRole` 和资源归属守卫；
- 不在没有权限 POC 结论前编写部门 ACL；
- 不在 P0 未完成前开始任何功能开发；
- 不把同步失败当成外部用户删除；
- 不将公司功能直接推送到 BlankPeng 的公共仓库。
