# 组织同步与身份状态

本文负责外部事实到本地投影的流程，以及身份、凭证、故障和回滚规则。数据字段见[数据库设计](./数据结构与事务.md)，请求授权见[权限设计](./权限判断与部门隔离.md)。

<a id="normal-flow"></a>
## 正常同步流程

```text
创建批次和采集代次
    -> 拉取部门、用户、用户部门关系
    -> 校验完整性与数据
    -> 匹配本地身份
    -> 生成差异和不可变计划
    -> 审批计划 hash
    -> 预检、逐对象应用
    -> 发布版本、结果和审计
```

| 步骤 | 具体动作 | 输出 |
| --- | --- | --- |
| 1. 建批次 | 在首个请求前分配单调 `snapshot_version`；固定身份源、配置和可见范围版本 | 批次号、输入版本、运行模式 |
| 2. 拉取 | 拉取部门树、用户及多部门关系；保存分页/游标检查点 | 规范化对象和来源证据 |
| 3. 校验 | 检查 ID 唯一、父节点存在、部门树无环、关系同来源；确认分页和范围完整性 | 完整快照或失败报告 |
| 4. 匹配 | 使用稳定外部 ID 查映射；新身份按证据匹配或进入冲突队列 | active 映射、候选、冲突 |
| 5. 差异 | 比较来源事实、贡献账本和目标版本；标明新增、更新、撤销及归属 | 不可变计划及逐项变更 |
| 6. 审批 | 审批人确认变化范围、风险和有效期，批准确切 `plan_hash` | 审批引用、到期时间 |
| 7. 应用 | 执行[应用协议](#apply)；每个对象完成后记录版本、结果和审计 | applied、partial 或 failed |
| 8. 发布 | 更新可消费的状态/策略版本，失效关联缓存，汇总计数 | 结果报告和可恢复检查点 |

`inspect` 结束于校验报告，`dry-run` 结束于计划输出，不改业务状态。`reconcile` 获取完整快照后走同一匹配、差异和应用流程。带有确定失效证据的安全处理见[身份状态](#identity-lifecycle)，不等待普通权限扩张审批。

分页必须遵循外部协议的结束条件：终止游标、末页或约定的短/空页，并校验异常中断。不能以固定页数或达到响应中的 `total` 作为完整性证明。必要分页失败时不发布完整快照，也不根据缺失项批量撤销。

## 身份匹配与部门关系

外部稳定键为 `provider_id + external_user_id`；部门键为 `provider_id + external_department_id`。本地用户 ID 由 WeKnora 生成。企业标识或 issuer 由身份源实例唯一约束，不用显示名作为主键。

匹配依次处理：

1. 存在唯一有效映射：继续使用，并校验当前外部状态。
2. 存在受控的显式绑定：验证双方账号归属与审批，建立映射。
3. 邮箱候选：检查双方唯一性、域名策略、外部邮箱可靠证明和本地账号归属证明。
4. 证明不足、多个候选或唯一性冲突：输出 `conflict`，由人工确认，不覆盖原映射。
5. 无匹配且批准创建本地用户：创建后绑定；创建与绑定要能关联同一变更。

基线注册接受用户提交的邮箱，不代表本地邮箱归属已验证。邮箱字符串相同只能生成候选，姓名相同不能自动合并。

同一 provider 的外部账号最多一个 active 映射，同一本地用户也最多绑定该 provider 的一个 active 外部账号；不同 provider 可以绑定同一本地用户。具体唯一索引见[身份表](./数据结构与事务.md#identity-tables)。

`revoked` 映射保持历史状态，重新绑定新建记录并引用旧映射，重新验证账号归属。用户部门关系为多对多，父部门关系单独保存；主部门仅为属性，不删除其他有效部门关系。部门移动生成关系的撤销与新增差异，权限继承规则由[权限设计](./权限判断与部门隔离.md#special-cases)定义。

<a id="projection"></a>
## 成员投影与贡献归属

人工、P1、P2 各保存独立贡献，不能只靠 `tenant_members` 的单行角色判断来源。投影使用当前有效贡献生成本地成员数据；请求采用哪些贡献由[授权来源](./权限判断与部门隔离.md#grants-and-limits)决定。

| 来源输入 | 投影动作 |
| --- | --- |
| 已确认 active 员工 | 默认贡献 `viewer` |
| 经批准参与知识维护 | 贡献 `contributor`，不改资源归属 |
| 外部管理员或部门负责人标记 | 保存属性，不自动提升角色 |
| 人工 admin、owner 或系统管理员授权 | 由原有受控管理流程处理，不归目录同步拥有 |
| 来源贡献失效 | 仅撤销该来源的贡献，再重算成员 |
| 人工 suspended 或本地封禁 | 保留独立阻断，不被同步覆盖 |

同步只修改自己拥有的贡献和明确批准的投影字段。人工角色、临时权限及其他身份源的有效记录不能被本来源覆盖。所有成员管理写入者都要维护贡献归属和版本；尚不能维护时，不启用成员投影。

成员投影不自动创建 Organization、多个 Tenant 或 API Key，不迁移知识库所属空间，不删除用户历史内容。部门策略和紧急授权的具体权限归属[权限设计](./权限判断与部门隔离.md#special-cases)。

<a id="apply"></a>
## 审批计划与应用

### 来源顺序

采集代次在开始拉取前分配。身份源有可靠版本/游标时一并记录；没有外部顺序保证时串行采集，使用本地代次和范围证据，不单靠完成时间或 `updated_at` 排序。

同一 provider 的快照接受、计划预检和实际应用需要互斥；等待审批不持有锁。完整低版本快照晚到时丢弃，不能替换已接受的高版本。采集失败留下编号空洞没有问题，编号不得复用。

权威的单用户停用/删除事件更新该对象与 `security_event_version`，使依赖旧 active 事实的快照和计划失效。不能从旧原始快照重新生成一个新编号计划来恢复有效性；须取得能覆盖该事件的新事实。

### 计划内容

计划固定以下输入，`plan_hash` 覆盖全部变更项、版本、归属、审批期限和操作范围：

| 输入 | 校验用途 |
| --- | --- |
| `snapshot_version`、`scope_version`、`config_version`、`policy_version` | 确认输入仍是当前可用来源与策略 |
| 各对象来源记录版本、`security_event_version` | 识别快照之后的状态事件 |
| `expected_record_version`、`expected_field_version` | 比较目标记录及拟修改字段 |
| `expected_owner`、`expected_last_change_id` | 确认同步仍拥有拟修改对象/字段 |
| `before`、`after`、`change_id`、`idempotency_key` | 明确差异、归属和重复执行结果 |
| 审批 hash、审批引用、有效期 | 只执行实际批准的计划 |

计划批准后不可修改；审批页面和执行器读取同一内容。计划过期、输入变动或差异更新均生成新计划并重新审批。

### apply 动作

1. 获取 provider 应用锁，读取最新来源、配置、策略、目标和审批状态。
2. 在任何业务写入前校验全部变更项。来源版本、完整性、hash 或有效期变化返回 `stale_plan`；目标版本或归属变化返回 `conflict`。两者都零写入，重新生成差异并审批。
3. 对每个对象执行 CAS，比较目标版本、归属、最后变更 ID 和适用的来源/安全版本；写入贡献、投影、变更记录和审计，递增版本。
4. CAS 失败时停止剩余操作，记录已完成项和失败项，批次为 `partial`。不能静默覆盖或现场重算后继续使用旧审批。
5. 全部成功才标记 `applied`；报告列出成功、冲突、未执行和重试项，发布相应版本。

整批预检不代替逐对象 CAS，因为人工修改仍可能发生在预检之后。应用不使用覆盖整个企业目录的大事务；对象内事务要求见[事务](./数据结构与事务.md#transactions)。

已成功的相同幂等键返回记录的成功结果，不重复创建或写入。若后续被其他变更覆盖，重复请求返回冲突，不能再次写回原 `after`。批次重试只针对已记录的未完成项，并重新校验其输入；过时项必须走新计划。

<a id="identity-lifecycle"></a>
## 身份状态与凭证

### 状态变化

外部身份状态与 provider 健康状态分开。未出现在列表中不直接变为 deleted，删除证据要求见[可见范围](#visibility)。

| 变化 | 本地处理 |
| --- | --- |
| active → disabled | 保留映射，禁止该来源认证和授权贡献；执行下述撤销流程 |
| 确认 deleted | 映射变为 revoked，失效该来源贡献；保留绑定及业务历史 |
| 解绑或 rebind | 原绑定失效；新绑定重新验证、审批，关联历史 |
| disabled → active | 取得更新且可靠的事实，生成恢复计划；不恢复旧凭证 |
| revoked 身份再次出现 | 新建映射，不把旧 revoked 记录改回 active |
| 本地账号封禁 | 阻断全部真人路径与用户绑定 Key，不依赖某个 provider |
| 单次请求失败、分页不完整 | 进入[故障降级](#freshness)，不将员工批量停用 |

企业全局离职若需要封禁本地账号，必须有明确的公司策略及可靠事件，不能仅从一条外部身份失效推断全局封禁。

### 撤销流程

任一绑定来源停用、删除、解绑或 rebind：

1. 接受可靠失效事实时立即建立用户级阻断，更新安全版本，不等待普通计划审批。
2. 停止失效来源贡献，保留人工和其他有效来源记录。
3. 撤销该用户**所有旧 access/refresh 会话，包含其他来源签发的旧会话**，以及所有旧用户绑定 API Key。
4. 确认持久化撤销完成，发布状态版本并失效缓存；失败保持阻断，报告 `partial`。
5. 本地账号未封禁时，允许通过另一有效来源重新认证。新会话只采用选定来源及有效人工贡献，旧会话、旧 Key 和失效来源授权不复活。

状态更新和撤销使用同一事务，或持久化 `revocation_pending` 屏障。请求、新登录、签发和刷新共享该用户屏障；屏障未完成时全部拒绝。清缓存不能代替持久化撤销。

优先复用已有 `RevokeTokensByUserID`、AuthToken 记录与 `ValidateToken`。只有并发签发/刷新验证发现缺口时，才评审用户级 `session_epoch` 扩展；不把全用户撤销版本放在单条 mapping 上。

### 可信会话来源

服务端会话或签名声明记录：

```text
local_user_id + authn_method + authn_provider_id
+ identity_mapping_id + issued_at + active_tenant_id
+ session / revocation_reference
```

provider 与 mapping 必须由认证结果确定，不能使用请求参数声明。刷新和切换 Tenant 保留来源并重新校验，不能借操作更换来源。旧会话缺少来源时，仅允许从可信数据唯一还原；不能还原则要求重新登录。

本地密码或应急登录是独立认证方式，须有明确批准的范围和策略，不自动继承失效外部来源的部门贡献。

### API Key 依赖

独立机器 Key 按自己的 principal、撤销、到期、能力与 scope 判断，不依赖员工会话，也不因为创建者的目录失败而自动失效。

用户绑定 Key 是后续扩展，不是基线已具备的能力。支持时必须明确记录用户、依赖 provider 和 mapping；不能将“创建者”当作身份依赖。来源失效按上面的全用户撤销规则独立撤销 Key，新登录不恢复旧 Key；新 Key 需重新审批依赖和 scope。

来源依赖 Key 的签发与使用遵循下一节时效判断；降级期间禁止签发新的依赖 Key。Key 不借真人 `session_epoch` 判断自身撤销。依赖信息、principal、撤销状态或必要本地记录不可读时拒绝。

<a id="freshness"></a>
## 故障降级与事实时效

### 正常请求判断

凭证未过期且未撤销、本地账号可用、撤销屏障完成后，再检查该请求选定的认证来源。所依赖 mapping 和外部身份必须 active，provider 必须 healthy 或 degraded；disabled/error 不可用。

`last_verified_at` 只在可靠外部证据确认事实时更新。本地审批、apply、Token 签发及 provider 的全局最近成功时间不能刷新某个用户的验证时间。请求依赖多个身份或部门事实时，取这些事实最早的确认时间。

当前演算使用 `max_stale_age = 24h`；生产值的决定点见[Q1](./阶段交付与待确认问题.md#open-questions)。

```text
last_verified_fresh =
    last_verified_at 存在
    AND 0 <= now - last_verified_at <= max_stale_age

healthy_source_usable =
    来源与映射 active
    AND last_verified_fresh

degraded_source_usable =
    来源与映射 active
    AND last_verified_fresh
    AND degraded_at 存在且 degraded_at <= now
    AND issued_at < degraded_at
    AND 0 <= now - degraded_at <= max_stale_age
```

缺失/未来验证时间、未来签发时间均拒绝。降级前凭证仍需未过期且未撤销；`issued_at == degraded_at` 不算降级前签发。两项年龄在 24h 边界上可通过，超过即拒绝。相同来源规则用于用户绑定 Key。

例：最后确认 active 已过 25 小时，2 小时前才降级，即使 Token 在降级前签发且未过期也拒绝。保存的 active 标记不代替事实年龄。

### 进入与维持降级

必要请求失败或快照不完整立即进入 degraded；连续失败阈值只影响告警升级，不延迟降级。首次 `healthy → degraded` 记录 `degraded_at`，重复失败不重置起点，外部已确认 disabled/deleted 也不被 degraded 覆盖。

降级期间：

- 允许按上述窗口使用降级前签发的有效凭证。
- 禁止新登录、刷新、绑定、提升权限和普通 apply。
- 不根据缺失列表做批量撤销，不延长事实验证时间。
- 必要本地状态不可读时直接拒绝，不使用旧允许缓存兜底。
- 可靠安全事件可通过专用收缩计划处理；恢复处理可消费新完整快照，但仍校验版本，不能恢复授权或签发凭证。

### 恢复

先完成完整拉取和范围对账，再处理已发现的权限收缩、身份失效及撤销屏障；随后归档降级起止时间、发布新版本并清除 degraded。权限扩张、重新绑定和新凭证在恢复完成后使用新审批，不重放降级前旧计划。

<a id="visibility"></a>
## 可见范围与删除

完整读取“当前应用可见的所有页”不等于读取全企业。provider 配置变化、授权缩小或用户移出可见部门，均可能导致列表缺失。

| 证据 | 处理 |
| --- | --- |
| 分页中断、范围不可证实 | `unknown`，不推断 deleted，不扩张授权 |
| 确认可见范围缩小 | `out_of_scope`；明确批准后只撤销移出范围的贡献，原因 `scope_removed` |
| 稳定范围下缺少用户但无权威结果 | 记录待核查，不能仅凭列表差异删除 |
| 有效明确停用事件 | 处理 disabled，不升级为 deleted |
| 稳定范围/完整性核对，且有权威删除事件或逐用户 deleted 结果 | 执行 deleted 与撤销流程 |

`scope_version` 与完整性证据参与计划审批和 apply 检查。无法确认的新关系不授予权限；历史未确认事实只能在[时效窗口](#freshness)内沿用，不能永久保留或不断刷新。

## 冲突、重试与回滚

### 失败处理

| 类型 | 动作 |
| --- | --- |
| 限流、网络中断、临时外部故障 | 按配置做有上限的退避重试，保留检查点；不得发布不完整快照 |
| 外部格式错误、树循环、重复 ID | 批次失败，输出脱敏对象和错误码，人工修复输入 |
| 映射冲突、证据不足 | 留在人工队列，不自动选择账号 |
| `stale_plan`、目标版本/所有权冲突 | 停止该计划，读取新状态生成差异并重新审批 |
| 部分应用、撤销失败 | 保留完成项和阻断状态，选择重试未完成项或受控补偿 |

错误记录包含批次、对象、错误码、可否重试和尝试次数，不包含 Token、Secret 或完整外部响应。管理端必须显示未执行项，不能将部分投影写回为“同步成功”。

### rollback 动作

回滚只撤销某个 change 仍拥有的变更。先检查当前值等于 `after`，且记录/字段版本等于该变更保存的 `post_*`，`last_change_id` 和字段归属仍匹配，再用 CAS 写回 `before`。成功后递增新版本，写新的回滚变更 ID 和审计；不倒退版本。

人工改动后再改回相同值（ABA）、其他变更接管、对象删除重建、父关系或相关策略变化均返回 `rollback_conflict`。仅“当前值等于目标值”不能证明可回滚。

回滚不恢复已确认 disabled/deleted、已撤销会话/Key、到期或人工撤销授权，也不移除安全阻断。需要恢复时取得新有效事实并走新批准计划；其他来源和人工贡献保持独立。

## 输出与验证入口

报告按批次展示输入版本、完整性、审批引用、每项 before/after、归属、成功/冲突/未执行计数及安全处理状态。差异计划、应用和回滚通过 `run_id → plan_id → change_id` 关联。
