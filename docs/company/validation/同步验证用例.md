# 同步验证用例

使用[同步正文](../组织同步与身份状态.md)的流程和状态规则。以下是预期用例，不表示已有真实实现；72 项脚本只覆盖其中能用简化模型演算的子集。

## 基础输入

时间与用户沿用[权限夹具](./权限验证夹具.md)。版本用例独立重置：

```text
来源：P1，完整快照 10，scope/config/policy 版本均 1
外部对象：record_version=7，security_event_version=1
目标：value=viewer，record_version=7，field_version=7
归属：owner=P1，last_change_id=previous
计划 A：上述输入版本，viewer -> contributor，change_id=A
审批：approved_hash=plan_hash，2026-10-08 17:00 +08:00 到期
```

脚本中 apply 返回 `applied/stale_plan/conflict`；rollback 返回 `rolled_back/rollback_conflict`。正式实现还需验证整批预检、逐项事务、partial 报告与持久化审计。

## 正常与异常矩阵

| 用例 | 输入变化 | 预期 |
| --- | --- | --- |
| 正常应用与回滚 | A 应用后目标版本为 8，再回滚 | 应用成功；回滚后 viewer、版本 9；再次回滚冲突 |
| 幂等重试 | 同一 change、幂等键再次请求 | 返回记录结果，无第二次写入；若已被后续变更覆盖则冲突 |
| 旧 active 计划 | A 待审批；B 快照 11 确认 disabled 并应用；再批准 A | `stale_plan`、零写入，disabled 不恢复 |
| 来源变动 | scope/config/policy/来源记录/安全事件任一版本增加 | `stale_plan`，重新生成差异和审批 |
| 审批变化 | 到期、hash 不一致或输入不完整 | `stale_plan`，零写入 |
| 目标版本变化 | 目标记录或字段版本增加 | `conflict`，零写入 |
| 所有者变化 | owner 或最后 change 被人工接管 | `conflict`，不覆盖人工修改 |
| 中途 CAS 失败 | 第一对象成功，第二对象发生冲突 | 停止后续项；报告 partial 和已完成项 |
| ABA 回滚 | A 写 contributor；人工改 admin，再改 contributor | 即使当前值相同也 `rollback_conflict` |
| 安全阻断后回滚 | A 后发生已确认失效 | 不移除安全状态、不恢复旧会话/Key |
| 同值但归属变化 | 目标仍为 after，但 last_change_id 已更改 | `rollback_conflict` |
| 低版本晚到 | 接受快照 11 后收到 10 | 不接受 10，当前版本仍为 11 |
| 从旧快照重新出计划 | 旧 raw active 事实已被新安全事件覆盖 | 新计划编号不使旧事实有效，需重新取证 |
| 删除重建目标 | 同名对象使用新身份/版本 | 旧计划不能命中新对象 |

## 身份、范围与凭证矩阵

| 用例 | 输入变化 | 预期 |
| --- | --- | --- |
| 同源重复映射 | P1:E1 与 P1:E2 都拟绑定 U1 | 第二 active 关系冲突，人工解决 |
| 多来源绑定 | P1:E1、P2:E1 均绑定 U1 | 可存在；会话只依赖一条来源 |
| 邮箱同名无证据 | 外部邮箱与注册邮箱相同，无本地归属证明 | 仅候选，不自动绑定 |
| rebind | 原 mapping revoked，外部身份再次出现 | 新 mapping 指向历史；旧记录不改回 active |
| 单源失效 | U8 的 P1 disabled，P2 active | 所有旧 P1/P2 会话及用户绑定 Key 撤销；撤销完成后允许 P2 新登录 |
| 新来源登录 | U8 经 P2 重新认证 | P2 与有效人工贡献参与；不使用 P1 部门 grant |
| 撤销途中请求 | 状态已接受，持久化 revocation_pending | 旧请求、新签发、刷新均拒绝；撤销失败保持阻断 |
| 同步暂时失败 | 分页/必要 API 失败 | degraded；无批量停用，不发布完整快照 |
| 重复失败 | 已 degraded 再失败 | degraded_at 保持首次起点，不能延期 |
| 范围缩小 | 应用可见部门减少 | out_of_scope，不标 deleted；批准后按 scope_removed 撤贡献 |
| 列表缺失 | 所有可见页完整，但无删除证据 | 待核查，不把完整可见列表当全企业 |
| 权威删除 | 稳定范围核对且有可靠 deleted 结果 | 处理 revoked 与撤销，保留业务数据 |
| 时效反例 | last_verified_at 为 25h 前、降级 2h 前、旧 Token 未到期 | 拒绝 |
| 恢复 | 新完整快照、已处理安全收缩与撤销 | 才清 degraded；扩张重新审批，不重放旧计划 |
| 独立机器 Key | 员工来源失效，Key 无个人依赖且有效 | 按自己的 principal/scope 判断 |

## 真实实现的补充证据

持久化阶段增加两向 active 唯一约束、不同数据库实现、人工写入版本、对象事务失败和重试测试。撤销阶段用实际并发签发/刷新与来源事件验证屏障，证明完成前无新凭证穿过。

每项保存输入提交、批次/计划/change、执行前后版本、状态与写入计数。幂等、partial、恢复和回滚不能仅用返回码证明，要查实际记录与审计。
