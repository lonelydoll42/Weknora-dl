# 企业化接入总体架构

## 1. 目标和非目标

### 目标

1. 让企业微信成为可替换的外部身份源适配器。
2. 将组织、部门、用户和成员状态稳定投影到 WeKnora。
3. 保留现有 RBAC 动作和归属守卫，通过独立资源范围门槛预研单 Tenant 部门隔离。
4. 保留后续接入 LDAP、OIDC 或其他企业目录的空间。
5. 让官方版本可以持续同步，减少核心代码冲突。
6. 公司一期使用一个主 Tenant，不按部门自动创建多个 Tenant。

### 当前非目标

- 不在本阶段实现企业微信 API 调用。
- 不在本阶段实现企业微信扫码登录或 OIDC 登录。
- 不在本阶段新增数据库迁移。
- 不在本阶段修改 `tenant_members`、`organizations` 或现有 RBAC 中间件。
- 不在本阶段承诺“部门天然等于一个 WeKnora 空间”或自动创建多个 Tenant。

## 2. 第一性原理和 TOC 约束

问题的本质不是“增加一个企业微信接口”，而是把外部身份和权限事实可靠地投影到已有资源模型中。

当前首要约束是把资源准入、动作能力和身份可信度分开。授权并集只能增加能力，不能自动形成隔离：

```text
同 Tenant 默认可见 + 部门 grant 并集
    -> 无部门绑定仍可读取
    -> 列表/检索/Agent 路径越过隔离意图
    -> 验收矩阵与公式矛盾
```

因此必须先明确资源范围门槛和来源局部的能力限制，再校验身份状态与同步的新旧顺序。身份链的另一个约束是：

```text
身份不稳定
    -> 用户重复或错绑
    -> 同步无法幂等
    -> 权限绑定漂移
    -> 无法安全撤销
```

因此预研顺序必须是：

```text
基线确认
  -> 身份模型
  -> 同步生命周期
  -> 权限语义
  -> 数据模型
  -> 代码位置
```

如果先写同步代码，后面改变用户匹配规则或部门权限语义，会导致迁移、回滚和权限修复同时发生，这是当前最需要避免的瓶颈。

## 3. 分层设计

```text
+-----------------------------+
| WeCom / LDAP / OIDC Adapter  |
| 拉取、分页、限流、字段转换    |
+--------------+--------------+
               |
               v
+-----------------------------+
| Identity Sync                 |
| 差异计算、幂等、重试、审计    |
+--------------+--------------+
               |
               v
+-----------------------------+
| Canonical Identity           |
| Provider / External User     |
| Department / Mapping         |
+--------------+--------------+
               |
               v
+-----------------------------+
| WeKnora Projection           |
| User / TenantMember          |
| Organization / Share         |
+--------------+--------------+
               |
               v
+-----------------------------+
| Permission Policy            |
| Existing RBAC + Company     |
| Department/Resource Binding  |
+-----------------------------+
```

各层职责：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Provider Adapter | 外部 API、分页、限流、字段转换 | 本地权限决定 |
| Identity Sync | 差异、幂等、状态迁移、失败重试 | 直接拼接 HTTP 路由 |
| Canonical Identity | 外部身份和本地用户的稳定关系 | 保存未经筛选的完整外部响应 |
| WeKnora Projection | 投影为本地用户和成员关系 | 解释企业微信业务规则 |
| Permission Policy | 计算资源访问能力 | 直接依赖企业微信 SDK |
| Audit | 记录变化和拒绝 | 保存密码、令牌和完整敏感响应 |

## 4. 与现有 WeKnora 模型的关系

已对 `d9585f7` 完成相关源码的静态核对；构建、基础测试和真实接口行为尚未验证：

| 现有模型 | 语义 | 企业化方案中的定位 |
| --- | --- | --- |
| `users` | 本地用户身份 | 本地登录和资源操作主体 |
| `tenant_members` | 用户在某个空间中的角色 | 基础空间准入和粗粒度 RBAC |
| `organizations` / `organization_tenant_members` | Tenant 加入跨空间组织 | 不是员工加入企业部门 |
| `kb_shares` | 知识库共享关系 | 适用于组织级资源共享 |
| `audit_logs` | 权限和操作审计 | 同步和权限变化的统一审计出口 |

重要区别：

```text
企业部门 != WeKnora Organization
企业部门 != WeKnora Tenant
组织共享权限 != 空间内 RBAC
```

如果把每个部门直接建成一个租户，会造成：

- 用户跨部门时出现多个空间成员关系；
- 知识库归属和部门归属混在一起；
- 空间级管理员权限被误当成部门级权限；
- 后续组织架构变化需要迁移资源归属。

推荐先把部门作为外部身份主体，只有经过权限 POC 证明确有必要时，才将其投影为本地权限绑定。

静态证据索引：

| 已核实行为 | 源码位置 |
| --- | --- |
| 同 Tenant 的 KB 访问检查直接通过，不含部门范围 | `internal/middleware/kb_access.go` 的 `resolveKBAccessOnce` |
| 组织共享上限为接收 Tenant 角色、组织 Tenant 成员角色、共享权限三维约束 | `internal/application/service/kbshare.go` 的 `CheckTenantKBPermission` |
| 共享 Agent 可提供其 KB 范围内的只读访问 | `internal/middleware/kb_access.go` 的 `resolveSharedAgentAccess` |
| 现有用户级全部 Token 撤销和逐请求持久化撤销检查 | `internal/application/repository/user.go` 的 `RevokeTokensByUserID`；`internal/application/service/user.go` 的 `ValidateToken` |
| RBAC 关闭时部分角色守卫只记录而不拒绝 | `internal/middleware/rbac.go` 的 `RequireRole` |

这些是原有行为，不是本次文档提交引入的漏洞，也不证明新的范围门槛、来源绑定或版本栅栏已经实现。

### 4.1 公司一期 Tenant 策略

公司一期默认使用一个主 Tenant：

```text
公司企业微信组织
        |
        v
一个主 WeKnora Tenant
        |
        v
部门作为外部权限策略主体
```

这个决策只解决一期的组织边界，不代表永久禁止多 Tenant。只有出现明确的业务隔离、数据隔离或独立运维需求时，才重新评估多 Tenant。

一期不做：

- 按部门自动创建 Tenant；
- 以 Tenant 代替部门；
- 通过创建多个 Tenant 规避权限模型设计；
- 因组织架构变化迁移知识库归属。

### 4.2 权限上限边界

完整公式以 [permission-design.md](./permission-design.md) 第 6 节为唯一依据，架构只保留四层边界：

```text
可信主体及路径硬门槛
    -> 用户/资源/action/路径范围门槛
    -> 来源 grant 局部裁剪 + 路径共同安全上限
    -> 合并同一主体已通过的路径结果
```

`department_grant_action_limit` 只作用于部门 grant，不能裁剪人工 admin 的管理能力；真正对所有来源生效的是独立 `platform_security_ceiling` 和各路径固有上限。组织共享和 API Key 的上限不适用于无关路径，不能将所有路径 ceiling 全局求交。

单主 Tenant 启用隔离后，普通成员对未绑定资源默认拒绝。`tenant_public` 只开放明确声明的动作给有效内部成员；人工源 Tenant admin/owner 有可审计的部门范围豁免，但不豁免身份和共同安全上限。跨 Tenant 共享须显式批准导出范围，内部成员不能借共享或 Agent 绕过部门门槛。Document/Chunk/Wiki、列表、详情、检索、引用和下载都必须解析并检查源资源。

### 4.3 访问路径必须分开计算

Tenant 成员、组织共享和 API Key 不是同一种主体，也不具备相同的前置条件。每条路径先在自己的边界内计算 capability，再按同一主体的适用路径合并：

| 访问路径 | 主体 | 必要前置条件 | 不自动要求 |
| --- | --- | --- | --- |
| Tenant 成员 | 本地用户 | 身份有效、会话有效、目标 Tenant 成员有效 | 不能借用组织共享或 API Key 能力 |
| 组织共享 | 本地用户 | 当前 Tenant 成员有效、组织 Tenant 成员有效、共享及范围许可有效 | 不要求源 Tenant 成员，但不能进入源 Tenant 管理面 |
| 共享 Agent | 本地用户 | 当前 Tenant 成员有效、Agent 共享有效、KB 范围及资源许可有效 | KB 只读，不隐含源 Tenant 管理能力 |
| API Key | 机器主体 | Key 有效、未过期、未撤销、能力和资源范围匹配 | 不使用真人会话；不能与真人路径跨主体合并 |

本地账号封禁是全部真人路径和绑定用户 Key 的硬阻断。某条外部身份停用/删除只使该来源认证及授权贡献失效，并撤销该用户全部旧真人会话和旧绑定 Key；账号未封禁时，允许经另一条有效来源重新认证，但只计算选定来源和有效人工贡献。组织共享及 Agent 不能替无效会话更换认证来源。企业全局离职必须由明确本地账号策略表达，不能推断自单来源停用。

资源创建者限制是独立的资源归属上限。部门策略表达“编辑明确绑定知识库内容”的业务目标时，不能预先假设它可以突破该上限；若目标基线无法表达安全的委托编辑，P4 只能记录能力缺口，不能在预研阶段改写核心 RBAC。

### 4.4 会话撤销和身份源降级边界

真人会话撤销采用本地用户级全量语义，优先复用已有 Token 撤销机制；`session_epoch` 仅是并发验证发现缺口后的候选扩展，不放在单条身份映射上。会话须有可信认证来源和 mapping；刷新与切换 Tenant 保留来源，不接受客户端换来源。状态变更、并发签发/刷新和全量撤销须共享事务或持久化撤销屏障，撤销完成前 fail-closed。

API Key 使用独立的 Key 级状态与 scope。候选用户绑定 Key 还要记录来源依赖；任一绑定身份可信度变化时撤销该用户全部旧绑定 Key，其他有效来源新登录也不能复活旧 Key。独立机器 Key 不继承个人部门 grant 或管理员范围豁免。

身份源 degraded 不等于用户停用。healthy/degraded 分支都检查该身份所依赖事实的 `now - last_verified_at`；降级分支另外检查 `now - degraded_at` 和 `issued_at < degraded_at`。两个年龄须同时不超过 `max_stale_age`，active 标记不得绕过时效。预研 24h 须业务和安全确认；最后确认 active 25h、降级 2h 的未过期旧 Token 必须拒绝。降级期间禁止新登录、刷新、绑定和普通 apply；恢复先完整对账，经受版本校验的专用计划完成权限收缩及撤销，再清除 degraded 并恢复经新审批的投影。必要本地状态不可读时 fail-closed。

### 4.5 计划和回滚的顺序边界

批次互斥不阻止旧审批计划覆盖新事实。来源快照在采集前分配单调版本，计划绑定来源/范围/配置/策略版本和目标记录/字段版本、所有权、变更 ID、审批 hash。apply 全量预检后逐对象 CAS；版本变化返回 `stale_plan/conflict`，必须重新生成并审批。rollback 还须匹配变更后版本和最后变更归属，值相同不排除人工修改后又改回的 ABA 情况；不倒退版本，不恢复已撤销凭证或已确认失效身份。详细协议见 [org-sync-design.md](./org-sync-design.md) 第 6、7 节。

## 5. 同步方向

推荐使用单向同步：

```text
企业微信 -> Canonical Identity -> WeKnora
```

本地人工操作的策略：

- 身份字段由外部身份源管理；
- 本地紧急权限可以临时覆盖，但必须设置过期时间；
- 本地覆盖不能修改外部部门成员关系；
- 同步时记录“外部计算结果”和“本地最终结果”；
- 冲突不静默覆盖，进入冲突表和管理报告。

## 6. 运行模式

| 模式 | 是否写库 | 用途 |
| --- | --- | --- |
| `inspect` | 否 | 检查外部数据质量和权限映射 |
| `dry-run` | 否 | 生成新增、更新、停用、冲突差异 |
| `apply` | 是 | 按已批准差异执行 |
| `reconcile` | 是 | 对账并处理外部删除或失效 |

首个 POC 只允许 `inspect` 和 `dry-run`。在没有稳定的用户匹配和回滚验证前，不进入 `apply`。

## 7. 关键设计决策

### 决策 A：外部 ID 不能作为本地用户 ID

本地用户 ID 由 WeKnora 生成；外部用户以如下组合键唯一识别：

```text
provider + issuer/corp_id + external_user_id
```

邮箱、手机号和姓名只用于匹配候选，不能作为永久主键。

### 决策 B：不把企业微信角色直接翻译为 WeKnora Owner

企业微信管理员身份和 WeKnora 空间 Owner 不是同一个安全域。自动同步最高默认只能得到预先配置的 `admin`，Owner 和系统管理员必须通过人工审批或受控配置产生。

### 决策 C：同步删除先停用，再决定是否清理

外部用户失效时：

1. 保留身份映射和历史审计；
2. 禁止该来源新登录；
3. 仅撤销该来源拥有的成员和部门贡献，保留其他有效及人工贡献；
4. 撤销全部旧真人会话和绑定用户 Key，不永久封禁另一个有效来源；
5. 不删除知识库、文档和审计记录；
6. 在确认窗口后再执行可选清理。

## 8. 需要通过 POC 决策的问题

1. 一期单主 Tenant 下，部门权限是否必须精确到知识库，还是只需要空间级角色？
2. 一个用户是否允许拥有多个部门的权限并集？
3. 外部组织架构变更后，历史知识库权限是否自动重算？
4. 管理员是否允许在 WeKnora 中临时授予额外权限？
5. 验证预研默认 `max_stale_age = 24h` 是否符合业务和安全要求；超过该窗口必须 fail-closed。
6. 父部门策略是否显式继承到子部门；默认应保持不继承，避免组织树变化导致权限扩大。
7. 部门负责人对非本人创建的知识库内容是否需要委托编辑；如果需要，目标基线是否能在不放宽删除、共享和管理权限的前提下表达？
8. 人工授权与同步授权冲突时，哪些字段由同步拥有，哪些字段由人工拥有；人工紧急授权的过期和撤销如何记录？
9. 验证已有 Token 撤销是否覆盖并发签发/刷新，必要时再评审用户级版本；验证多身份源全部旧凭证撤销和新来源重登录。
10. 验证 revoked 映射新建 rebind 记录、历史保留和 active 唯一约束在目标数据库上的实现方式。
11. 明确 `deny_with_gap` 的缺口责任人、复核日期和业务/安全共同批准记录。
12. 验证同一身份源下本地用户 active 外部账号唯一，以及不同身份源绑定同一本地用户的登录选择和撤销语义。
13. 验证 `external_department` 权限主体始终使用 `provider_id + subject_ref`，不允许只凭外部部门 ID 判定主体。
14. 确认未绑定默认拒绝、公共动作、人工管理员范围豁免、共享导出和创建初始绑定的业务可用性。
15. 验证旧计划不能恢复停用、CAS/ABA 回滚、贡献账本与全入口版本更新；完整可见列表不能独立证明删除。
