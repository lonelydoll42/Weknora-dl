# 企业化接入总体架构

## 1. 目标和非目标

### 目标

1. 让企业微信成为可替换的外部身份源适配器。
2. 将组织、部门、用户和成员状态稳定投影到 WeKnora。
3. 在不重写现有 RBAC 的前提下，支持公司权限策略预研。
4. 保留后续接入 LDAP、OIDC 或其他企业目录的空间。
5. 让官方版本可以持续同步，减少核心代码冲突。
6. 公司一期使用一个主 Tenant，不按部门自动创建多个 Tenant。

### 当前非目标

- 不在本阶段实现企业微信 API 调用。
- 不在本阶段实现企业微信扫码登录或 OIDC 登录。
- 不在本阶段新增数据库迁移。
- 不在本阶段修改 `tenant_members`、`organizations` 或现有 RBAC 中间件。
- 不在本阶段承诺“部门天然等于一个 WeKnora 空间”或自动创建多个 Tenant。

## 2. 第一性原理和 TOC 约束

问题的本质不是“增加一个企业微信接口”，而是把外部身份和权限事实可靠地投影到已有资源模型中。

当前最大的约束是“身份边界和权限边界没有被明确分开”：

```text
身份不稳定
    -> 用户重复或错绑
    -> 同步无法幂等
    -> 权限绑定漂移
    -> 无法安全撤销
```

因此预研顺序必须是：

```text
基线确认
  -> 身份模型
  -> 同步生命周期
  -> 权限语义
  -> 数据模型
  -> 代码位置
```

如果先写同步代码，后面改变用户匹配规则或部门权限语义，会导致迁移、回滚和权限修复同时发生，这是当前最需要避免的瓶颈。

## 3. 分层设计

```text
+-----------------------------+
| WeCom / LDAP / OIDC Adapter  |
| 拉取、分页、限流、字段转换    |
+--------------+--------------+
               |
               v
+-----------------------------+
| Identity Sync                 |
| 差异计算、幂等、重试、审计    |
+--------------+--------------+
               |
               v
+-----------------------------+
| Canonical Identity           |
| Provider / External User     |
| Department / Mapping         |
+--------------+--------------+
               |
               v
+-----------------------------+
| WeKnora Projection           |
| User / TenantMember          |
| Organization / Share         |
+--------------+--------------+
               |
               v
+-----------------------------+
| Permission Policy            |
| Existing RBAC + Company     |
| Department/Resource Binding  |
+-----------------------------+
```

各层职责：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Provider Adapter | 外部 API、分页、限流、字段转换 | 本地权限决定 |
| Identity Sync | 差异、幂等、状态迁移、失败重试 | 直接拼接 HTTP 路由 |
| Canonical Identity | 外部身份和本地用户的稳定关系 | 保存未经筛选的完整外部响应 |
| WeKnora Projection | 投影为本地用户和成员关系 | 解释企业微信业务规则 |
| Permission Policy | 计算资源访问能力 | 直接依赖企业微信 SDK |
| Audit | 记录变化和拒绝 | 保存密码、令牌和完整敏感响应 |

## 4. 与现有 WeKnora 模型的关系

目标基线预期需要核实四类重要能力。当前分支已接入源码基线，但尚未完成能力和行为验证，下面的名称和语义不能替代 P0 的源码核对：

| 现有模型 | 语义 | 企业化方案中的定位 |
| --- | --- | --- |
| `users` | 本地用户身份 | 本地登录和资源操作主体 |
| `tenant_members` | 用户在某个空间中的角色 | 基础空间准入和粗粒度 RBAC |
| `organizations` / 组织成员关系 | 跨空间协作 | 适用于跨空间共享，不等同于企业部门 |
| `kb_shares` | 知识库共享关系 | 适用于组织级资源共享 |
| `audit_logs` | 权限和操作审计 | 同步和权限变化的统一审计出口 |

重要区别：

```text
企业部门 != WeKnora Organization
企业部门 != WeKnora Tenant
组织共享权限 != 空间内 RBAC
```

如果把每个部门直接建成一个租户，会造成：

- 用户跨部门时出现多个空间成员关系；
- 知识库归属和部门归属混在一起；
- 空间级管理员权限被误当成部门级权限；
- 后续组织架构变化需要迁移资源归属。

推荐先把部门作为外部身份主体，只有经过权限 POC 证明确有必要时，才将其投影为本地权限绑定。

### 4.1 公司一期 Tenant 策略

公司一期默认使用一个主 Tenant：

```text
公司企业微信组织
        |
        v
一个主 WeKnora Tenant
        |
        v
部门作为外部权限策略主体
```

这个决策只解决一期的组织边界，不代表永久禁止多 Tenant。只有出现明确的业务隔离、数据隔离或独立运维需求时，才重新评估多 Tenant。

一期不做：

- 按部门自动创建 Tenant；
- 以 Tenant 代替部门；
- 通过创建多个 Tenant 规避权限模型设计；
- 因组织架构变化迁移知识库归属。

### 4.2 权限上限边界

部门授权只能产生候选 capability，最终结果必须同时受到以下边界限制：

```text
effective_capability
    = applicable_grants
    INTERSECT applicable_ceilings

applicable_ceilings =
    Tenant RBAC 上限
    INTERSECT 资源归属上限
    INTERSECT 组织共享上限
    INTERSECT 部门策略上限
    INTERSECT API Key capability 上限（仅 API Key 路径）
```

部门策略不得绕过现有空间角色、资源创建者约束、组织共享关系或 API Key 的声明能力。

### 4.3 访问路径必须分开计算

Tenant 成员、组织共享和 API Key 不是同一种主体，也不具备相同的前置条件。每条路径先在自己的边界内计算 capability，再按同一主体的适用路径合并：

| 访问路径 | 主体 | 必要前置条件 | 不自动要求 |
| --- | --- | --- | --- |
| Tenant 成员 | 本地用户 | 身份有效、会话有效、目标 Tenant 成员有效 | 不能借用组织共享或 API Key 能力 |
| 组织共享 | 本地用户 | 身份有效、会话有效、组织成员有效、共享关系有效 | 不自动要求目标 Tenant 成员资格，但不能进入目标 Tenant 管理面 |
| API Key | 机器主体 | Key 有效、未过期、未撤销、能力和资源范围匹配 | 不使用真人会话；不能与真人路径跨主体合并 |

外部身份停用、删除、本地撤销和安全封禁属于全局硬阻断。API Key 如果绑定了本地用户或服务主体，还必须叠加该主体的状态阻断。组织共享不能成为绕过停用状态的替代登录路径。

资源创建者限制是独立的资源归属上限。部门策略表达“编辑明确绑定知识库内容”的业务目标时，不能预先假设它可以突破该上限；若目标基线无法表达安全的委托编辑，P4 只能记录能力缺口，不能在预研阶段改写核心 RBAC。

### 4.4 会话撤销和身份源降级边界

真人会话撤销版本归属于本地用户或现有会话机制，不归属于单条外部身份映射。Token 携带本地用户标识和签发时的 `session_epoch` 或等价版本；任一绑定身份发生影响登录可信度的停用、删除、解绑或重新绑定时，递增本地用户版本，撤销该用户全部真人会话。一个本地用户绑定多个身份源时，不能只撤销某一条映射对应的 Token。

API Key 使用独立的 Key 级 active、过期、撤销和 scope 检查；绑定本地用户的 API Key 还要检查本地用户状态，但不使用真人 Token 的会话版本。

身份源 `provider_degraded` 只表示外部事实暂时不可刷新，不等同于用户已经停用。预研默认 `max_stale_age = 24h`，但它不是最终生产决策；进入 POC 前必须由业务和安全评审确认。降级期间只有 `degraded_at` 之前签发、尚未过期且撤销检查通过的 Token 可以沿用最后一次确认的 active 状态，禁止新登录、Token 刷新、身份绑定、成员投影、权限提升和 apply；超过 stale 窗口，或本地用户状态、会话撤销版本、Tenant 成员或共享关系不可读取时，所有依赖该身份源外部事实的真人请求必须 fail-closed。独立 API Key 按自身 active、过期、撤销和 scope 判断，不因真人 stale 窗口自动拒绝；绑定本地用户的 API Key 还要检查本地用户状态，但不使用真人 Token 的 `session_epoch`。API Key 的本地撤销状态不可读取时仍然 fail-closed。provider 恢复后先完成完整对账，再恢复投影和清除降级状态。

## 5. 同步方向

推荐使用单向同步：

```text
企业微信 -> Canonical Identity -> WeKnora
```

本地人工操作的策略：

- 身份字段由外部身份源管理；
- 本地紧急权限可以临时覆盖，但必须设置过期时间；
- 本地覆盖不能修改外部部门成员关系；
- 同步时记录“外部计算结果”和“本地最终结果”；
- 冲突不静默覆盖，进入冲突表和管理报告。

## 6. 运行模式

| 模式 | 是否写库 | 用途 |
| --- | --- | --- |
| `inspect` | 否 | 检查外部数据质量和权限映射 |
| `dry-run` | 否 | 生成新增、更新、停用、冲突差异 |
| `apply` | 是 | 按已批准差异执行 |
| `reconcile` | 是 | 对账并处理外部删除或失效 |

首个 POC 只允许 `inspect` 和 `dry-run`。在没有稳定的用户匹配和回滚验证前，不进入 `apply`。

## 7. 关键设计决策

### 决策 A：外部 ID 不能作为本地用户 ID

本地用户 ID 由 WeKnora 生成；外部用户以如下组合键唯一识别：

```text
provider + issuer/corp_id + external_user_id
```

邮箱、手机号和姓名只用于匹配候选，不能作为永久主键。

### 决策 B：不把企业微信角色直接翻译为 WeKnora Owner

企业微信管理员身份和 WeKnora 空间 Owner 不是同一个安全域。自动同步最高默认只能得到预先配置的 `admin`，Owner 和系统管理员必须通过人工审批或受控配置产生。

### 决策 C：同步删除先停用，再决定是否清理

外部用户失效时：

1. 保留身份映射和历史审计；
2. 禁止新登录；
3. 停用或撤销本地空间成员关系；
4. 撤销会话和临时权限；
5. 不删除知识库、文档和审计记录；
6. 在确认窗口后再执行可选清理。

## 8. 需要通过 POC 决策的问题

1. 一期单主 Tenant 下，部门权限是否必须精确到知识库，还是只需要空间级角色？
2. 一个用户是否允许拥有多个部门的权限并集？
3. 外部组织架构变更后，历史知识库权限是否自动重算？
4. 管理员是否允许在 WeKnora 中临时授予额外权限？
5. 验证预研默认 `max_stale_age = 24h` 是否符合业务和安全要求；超过该窗口必须 fail-closed。
6. 父部门策略是否显式继承到子部门；默认应保持不继承，避免组织树变化导致权限扩大。
7. 部门负责人对非本人创建的知识库内容是否需要委托编辑；如果需要，目标基线是否能在不放宽删除、共享和管理权限的前提下表达？
8. 人工授权与同步授权冲突时，哪些字段由同步拥有，哪些字段由人工拥有；人工紧急授权的过期和撤销如何记录？
9. P0 源码核对时确认现有会话机制如何落地本地用户级 `session_epoch`，并验证多身份源用户的全量真人会话撤销。
10. 验证 revoked 映射新建 rebind 记录、历史保留和 active 唯一约束在目标数据库上的实现方式。
11. 明确 `deny_with_gap` 的缺口责任人、复核日期和业务/安全共同批准记录。
12. 验证同一身份源下本地用户 active 外部账号唯一，以及不同身份源绑定同一本地用户的登录选择和撤销语义。
13. 验证 `external_department` 权限主体始终使用 `provider_id + subject_ref`，不允许只凭外部部门 ID 判定主体。
